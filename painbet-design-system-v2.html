Reference document · not a marketing page

Design system reference

Every view, modal, component and interaction state in the built pain.bet front end, specified for two audiences: engineers wiring a real backend into the existing HTML/CSS/JS, and designers extending the product without drifting from it. Ground truth is index.html; where USER_JOURNEYS.md and the live code disagree, the code wins — every such case is called out inline.

How to read this document Component demos render with the product's real class names on the product's real dark ground — copy the code block under each one directly into index.html. Doc chrome (this sidebar, headings, tables) is a separate visual system so nothing here is mistaken for shippable UI. Toggle the button top-right to check this document's own legibility in light and dark — the product itself stays dark-only regardless.
Macrostructure

Long Document — a linear, numbered reference with a sticky side rail, chosen because the brief is a lookup tool ("what does this look like, in this state, at this width"), not a persuasive page. See report footer for full rationale.

Theme

Not a catalog pick. This is a system-managed brand — arterial red #e0163c and morphine blue #7FD6E8 are preserved from the live build and extended, never replaced.

Scope

Foundations → every component in §11 → all 15 modals → nav/layout → every journey in §04–09 → responsive → voice → full token table → open questions.

01 Foundations

Colour

Two chromatic accents carry all brand meaning. Arterial red is pain, risk, action — every primary CTA, every "this costs you something" moment. Morphine blue is money coming back — rakeback, cashback, payouts, proof — and is never used for a generic action, a generic success state, or a generic accent. Everything else is neutral: ink on glass on a near-black ground.

Resolved token conflicts index.html defines several colour tokens twice with different values, depending on whether an element sits inside the .v5m-scoped subtree or the top-level B71-native pages (see HANDOFF.md's two-page-system note). This document picks one canonical value per token and states why:
  • --blood / --red — canonical #e0163c. A second global :root block redeclares --red:#E10600 outside .v5m; that's a near-duplicate of the brand red, not an intentional second colour. Recommend deleting the redeclaration so --red simply aliases --blood everywhere.
  • --bg — canonical #101114. The top-of-file :root declares --bg:#07080a, but the actual visible ground is .ambient{background:#101114}, a fixed layer painted over body (confirmed in HANDOFF.md — a vignette that faded to var(--bg) instead of #101114 shipped as a visible seam bug once already). Any new gradient that fades "to background" must target #101114.
  • --card / --card-2 / --card-hi vs --glass / --glass-border — canonical is the --glass family. The two token sets describe the same visual role (translucent dark surface) with different names depending on scope. This document keeps --card* as deprecated aliases pointing at --glass* so existing markup keeps working during a migration, rather than a hard break.

Contrast flags
  • --ink-lo #6b7078 is 3.79:1 on the page ground — below 4.5:1. It already reads correctly in the live build because it's reserved for uppercase mono meta text at 8.5–10px, never body copy — but that constraint isn't enforced anywhere. This document scopes it explicitly to labels/timestamps and flags it as a "do not use for sentences" token.
  • --blood #e0163c as a text colour (kickers, section tags) is 3.91:1 — passes for large/bold text (≥18.66px bold) but fails 4.5:1 for anything smaller. In practice it's used at 10–11px uppercase mono, which is below the large-text threshold — technically a fail. Recommend either promoting kicker text to --redhi (5.05:1) or accepting it as a deliberate brand-voice exception the way many editorial systems treat small kicker text.
  • #fff on --redhi (button hover state) is 3.74:1 — fails 4.5:1 for normal text, passes only for large/bold text. Button labels are 10.5–11.5px bold uppercase mono, under the large-text cutoff. This is a real, measured gap in the hover state specifically (the resting .btn.red state at 4.83:1 passes). Flagged, not fixed silently — a product decision either lightens the hover red or accepts the AA gap on a transient two-state interaction.

Colour usage rules

  • Red = you're about to spend or risk something. Deposit, place bet, confirm stake, danger zone actions.
  • Blue = you're getting something back. Rakeback drip, cashback, Anesthesia payback, withdrawal success, proof-of-reserves. Never a secondary button colour, never a generic "info" tint.
  • Never mix them on the same control. A single button is either red (spend) or blue (receive), never both.
  • Success ≠ blue. A saved profile, a passed 2FA check, a completed upload use --success green, not morphine blue — blue stays reserved for money.

Type

Three faces, one strict division of labour. Archivo Black is the only display face — heavy, condensed, always uppercase. Archivo carries body copy. JetBrains Mono (falling back to SF Mono / system mono) carries the clinical voice: every label, ID, amount, timestamp and tag is set in mono, uppercase, and letter-spaced — this is the single most distinctive typographic signal in the product and should never be swapped for the sans face on data.

Two motion categories — do not merge them Per explicit client direction (USER_JOURNEYS.md §12): ambient motion — the ticker, the EKG traces, the provider marquee, the neuron cinematic — plays regardless of OS prefers-reduced-motion. It's part of the brand's pulse, not a decorative flourish. Functional motion — modal enter/exit, drawer slide, toast, odds-change flash — must still respect prefers-reduced-motion: reduce, collapsing to a ≤150ms opacity crossfade. Keep these in genuinely separate CSS so a future refactor can't accidentally silence the ambient layer while "fixing" reduced-motion support, or vice versa. 
/* functional motion — respects reduced motion */
.modalbox, .betslip, .toast { transition: transform var(--dur-slow) var(--ease-out), opacity var(--dur-slow) var(--ease-out); }
@media (prefers-reduced-motion: reduce) {
  .modalbox, .betslip, .toast, .sheet-demo { transition-duration: 150ms !important; transform: none !important; }
}

/* ambient motion — intentionally OUTSIDE any reduced-motion query */
.ticker .track, .marquee-row, .ekg svg, .neuron-canvas { animation-play-state: running !important; }

Idle → pulse → activation → mark, playing behind/over the admissions form on submit. Non-disclosure copy — password recovery

Destructive / irreversible actions — double confirmation

Self-exclusion and account closure share one pattern: state the consequence in plain language, require an explicit second confirmation (not just "are you sure?"), and never pre-check the confirming control.

09 Appendix

Open questions

Genuinely ambiguous items the source material left unresolved. These are flagged, not answered — several are business decisions, not design ones.

Drops promo dead end

HANDOFF.md confirms the drops promo's Go button just closes the modal — no Dispensary/Drops page exists anywhere in the site. Not a bug, but not designed here either: building a destination page would be inventing a feature, not documenting one.

Sign-in → account routing gap

HANDOFF.md notes markSignedIn()'s topbar swap has never been re-verified against The Chart's current build — whether sign-in should route somewhere specific post-auth is an open question from the original team, not something this document can settle without a product decision.

Demo mode

J1 and the Game launch modal both flag demo mode as unresolved. If it ships, it needs a persistent DEMO marker and must never touch balance, loyalty or history — a constraint stated here, not a shipped design.

PainKillers redemption

PK accrue with no spend surface. A currency that only accumulates isn't a currency yet — this is a product/economy decision (what does PK buy, at what rate) that a design system can't invent on its behalf.

Support escalation

No ticket history or escalation path exists (J23). A user with an ongoing issue has nowhere to check status — flagged, not designed, since it depends on what support tooling actually exists behind Triage.

Contrast on the hover-red button state

White text on --redhi measures 3.74:1 — below 4.5:1, though the small bold uppercase button text sits under the "large text" AA threshold either way. A product call is needed: lighten the hover red, or accept the gap on a transient two-state interaction. See §01 Colour.

Mobile balance pill wrap

HANDOFF.md notes the 147px balance pill ("USDT 2,840 · PK 1,250") sometimes wraps to two lines on narrow phones — not overflow, not broken, just not tight. Left as a known minor gap rather than silently "fixed" without seeing it rendered.

Breakpoint consolidation is a target, not a completed migration

§06 sets four/five canonical breakpoints for new work. It does not claim index.html's twelve existing ad hoc values have already been folded into them — that's a follow-up engineering pass, out of scope for a reference document.

09 Appendix

Slop test

Hallmark's 69-gate slop test is scoped for greenfield marketing pages; several gates (invented metrics, hero enrichment tier, nav/footer archetype diversification) don't map cleanly onto a documentation build. Judged in that context, against the universal gates that do apply:

  • No invented metrics — every number in this document (token values, contrast ratios, breakpoint counts) is either measured directly (WCAG relative-luminance contrast, computed against the resolved token values) or lifted verbatim from index.html/USER_JOURNEYS.md. Nothing is a placeholder stat dressed up as real data.
  • Locked tokens — every colour and font-family reference in the product-component CSS routes through a named custom property; nothing improvises a raw hex mid-rule.
  • No re-drawn chrome — no fake browser bars, phone frames, or IDE chrome anywhere in the document.
  • Mobile responsiveness — checked at 390/600/900/1100px; sidebar collapses to a stacked nav below 900px, demo grids collapse to one column below 600px, no horizontal scroll on the doc shell itself (component code blocks scroll internally, by design).
  • Focus-visible — every interactive doc-chrome and product-demo control carries a visible focus ring at ≥3:1 contrast, shown instantly, never animated in.
  • Contrast — audited explicitly in §01 rather than assumed; three genuine sub-4.5:1 findings are flagged rather than hidden.
